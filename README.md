# Inventory Management System

ระบบ Backend และหน้าเว็บสำหรับจัดการคลังสินค้าขนาดเล็ก เน้น 3 เรื่อง: **ตัวเลขสต็อกต้องถูกต้องเสมอ**, **ทุกการเปลี่ยนแปลงต้องตรวจย้อนหลังได้**, และ **เห็นสินค้าใกล้หมดได้ทันที**

สร้างด้วย Node.js (Express) และ PostgreSQL ไม่มี build step ฝั่งหน้าเว็บ

## ฟีเจอร์

- เพิ่มสินค้า (ชื่อ, SKU ไม่ซ้ำ, ราคาทุน, หมวดหมู่, สต็อกเริ่มต้น)
- ปรับสต็อกเพิ่ม/ลด ระบบกันสต็อกติดลบ และบันทึกประวัติทุกครั้ง พร้อมเหตุผล
- แถบเตือนสินค้าใกล้หมด (คงเหลือน้อยกว่า 5 ชิ้น) กดเพื่อเติมสต็อกได้ทันที
- ค้นหาจากชื่อ/SKU, กรองตามหมวดหมู่, แบ่งหน้า
- ดูประวัติการเพิ่ม/ลดสต็อกรายสินค้า (ก่อน → หลัง, เวลา, เหตุผล)
- หน้าเว็บใช้ได้ทั้งคอมพิวเตอร์และมือถือ
- โหมดมืด/สว่าง สลับด้วยสวิตช์มุมขวาบน ระบบจำค่าที่เลือกไว้ และถ้ายังไม่เคยเลือกจะตามการตั้งค่าของเครื่อง

## เริ่มใช้งาน

ต้องมี **Node.js 18 ขึ้นไป** และ **Docker**

```bash
# 1. สร้างไฟล์ตั้งค่า (ค่าเริ่มต้นใช้งานได้เลย)
cp .env.example .env

# 2. เปิดฐานข้อมูล PostgreSQL (สร้างตารางและหมวดหมู่ตั้งต้นให้อัตโนมัติ)
docker compose up -d

# 3. ติดตั้งและรัน
npm install
npm start          # หรือ npm run dev เพื่อให้รีสตาร์ทอัตโนมัติเมื่อแก้โค้ด
```

เปิด <http://localhost:3000> เพื่อใช้หน้าเว็บ และ <http://localhost:3000/api/health> เพื่อตรวจว่า API เชื่อมฐานข้อมูลได้

**หมายเหตุ**
- ไฟล์ `db/schema.sql` ทำงานตอนสร้างฐานข้อมูลครั้งแรกเท่านั้น ถ้าแก้ schema แล้วอยากเริ่มใหม่ ให้รัน `npm run db:reset` (ลบข้อมูลทั้งหมด)
- ถ้าพอร์ต 5432 ถูกใช้อยู่ ให้เปลี่ยน `DB_PORT` ใน `.env`
- หยุดฐานข้อมูล: `npm run db:down`

## การตัดสินใจออกแบบ

### 1. ปรับสต็อกอย่างไรไม่ให้ติดลบแม้มีคนกดพร้อมกัน

ปัญหาคลาสสิกคืออ่านสต็อก → คำนวณ → เขียนกลับ ถ้าสองคำขออ่านค่าเดียวกัน (เช่น 1 ชิ้น) แล้วต่างลด 1 ผลจะเป็นลบหรือยอดหาย แก้โดยทำทั้งหมดใน DB transaction เดียว และ lock แถวสินค้าก่อนอ่าน

```sql
BEGIN;
SELECT stock_quantity FROM products WHERE id = $1 FOR UPDATE;   -- คำขออื่นของสินค้าเดียวกันต้องรอตรงนี้
-- ตรวจใน Node: สต็อก + change ต้อง >= 0 ไม่งั้น throw 409 (ROLLBACK)
UPDATE products SET stock_quantity = $2, updated_at = NOW() WHERE id = $1;
INSERT INTO stock_transactions (...) VALUES (...);              -- บันทึกประวัติใน transaction เดียวกัน
COMMIT;
```

เหตุผลที่เลือกวิธีนี้:
- **ถูกต้องและอ่านง่าย** คำขอของสินค้าเดียวกันต่อคิวกัน ส่วนสินค้าคนละชิ้นไม่ขวางกัน
- **สต็อกกับประวัติไม่มีทางไม่ตรงกัน** เพราะสำเร็จหรือล้มเหลวพร้อมกัน ถ้า INSERT ประวัติพัง สต็อกก็ ROLLBACK ตาม
- **มีด่านสุดท้ายในฐานข้อมูล** `CHECK (stock_quantity >= 0)` กันไว้อีกชั้น แม้ logic ใน API จะพลาด

ทางเลือกที่พิจารณาแล้วไม่เลือก: `UPDATE ... SET stock = stock + $1 WHERE stock + $1 >= 0` ก็ atomic เช่นกัน แต่ต้องการค่า `stock_before` สำหรับประวัติและต้องแยกแยะ "ไม่พบสินค้า" กับ "สต็อกไม่พอ" ซึ่ง `FOR UPDATE` ตอบได้ตรงกว่า ส่วน optimistic lock (version + retry) ซับซ้อนกว่าที่งานนี้ต้องการ

**ตรวจได้เองด้วย** `npm run race-test` สคริปต์จะสร้างสินค้าสต็อก 15 แล้วยิงคำขอ "ลด 1" พร้อมกัน 30 ครั้ง ผลที่ถูกต้องคือสำเร็จ 15 / ถูกปฏิเสธ 15 (HTTP 409) สต็อกเหลือ 0 และผลรวมประวัติตรงกับสต็อก

### 2. เก็บยอดคงเหลือไว้ที่สินค้า และเก็บประวัติแบบ ledger

- `products.stock_quantity` เก็บยอดปัจจุบัน เพื่อให้ดึงรายการและ low-stock ได้เร็วโดยไม่ต้อง SUM ประวัติทุกครั้ง
- `stock_transactions` เพิ่มอย่างเดียว ไม่แก้ไขไม่ลบ และเก็บ `stock_before` / `stock_after` ไว้ ถ้ายอดเพี้ยนในอนาคตจะหาจุดที่เริ่มผิดได้
- สร้างสินค้าพร้อมสต็อกเริ่มต้นจะบันทึกรายการ `IN` "Initial stock" ให้ด้วย ผลรวมประวัติจึงตรงกับยอดเสมอ
- เรียงประวัติด้วย `id` ไม่ใช่ `created_at` เพราะ `NOW()` คือเวลาเริ่ม transaction ซึ่งอาจสลับลำดับเมื่อมีคำขอพร้อมกัน ส่วน `id` ถูกสร้างหลังได้ lock แล้ว จึงตรงกับลำดับจริง

### 3. ตรวจข้อมูลสองชั้น และ error รูปแบบเดียว

- ชั้นแรกที่ API (`validators.js`) บอกทุกฟิลด์ที่ผิดในครั้งเดียว ชั้นสองที่ฐานข้อมูล (UNIQUE, CHECK, FOREIGN KEY)
- เคส SKU ซ้ำจากสองคำขอพร้อมกัน ให้ UNIQUE ในฐานข้อมูลเป็นผู้ตัดสิน แล้วแปลงเป็น `409 DUPLICATE_SKU` แทนที่จะ "เช็กก่อนแล้วค่อยเพิ่ม" ซึ่งมีช่องโหว่
- SKU ถูกตัดช่องว่างและแปลงเป็นตัวพิมพ์ใหญ่ ไม่ให้ `kb-001` กับ `KB-001` เป็นสินค้าคนละตัว
- Error ทุกตัวอยู่ในรูป `{ "error": { "code", "message", "details?" } }` และ error ที่ไม่คาดคิดจะไม่เปิดเผยรายละเอียดภายในออกไป

### 4. หน้าเว็บ

- HTML/CSS/JS ล้วน เสิร์ฟจาก Express เลย ไม่ต้อง build ลดขั้นตอนตอนตรวจงาน
- ข้อความจากผู้ใช้ (ชื่อสินค้า เหตุผล) ใส่ผ่าน `textContent` เสมอ ไม่ใช้ `innerHTML` จึงไม่เกิด XSS
- ฟอร์มปรับสต็อกแสดงพรีวิว "คงเหลือหลังปรับ 3 → 1" และปิดปุ่มทันทีถ้าลดเกิน ผู้ใช้ไม่ต้องรอ error จากเซิร์ฟเวอร์
- ถ้าระหว่างที่เปิดฟอร์มมีคนอื่นปรับสต็อกจนไม่พอ ระบบอัปเดตตัวเลขในฟอร์มให้และให้ตัดสินใจใหม่
- สินค้าใกล้หมดมีช่องไฟเติมตามจำนวนที่เหลือ ดูได้ทันทีว่าใกล้ศูนย์แค่ไหน
- สีทั้งหมดเป็น CSS variable ชุดเดียว โหมดมืดเปลี่ยนแค่ค่าตัวแปร (ไม่มีสไตล์ซ้ำ) ตั้งธีมก่อนวาดหน้าจึงไม่มีหน้าขาววูบเมื่อเปิดในโหมดมืด และตรวจอัตราส่วนความคมชัดของข้อความหลักแล้วผ่านเกณฑ์ 4.5:1 ทั้งสองโหมด

## การทดสอบ

```bash
npm test            # unit + API test (Jest, Supertest) ไม่ต้องเปิดฐานข้อมูล
npm run race-test   # ทดสอบพร้อมกันกับ API และฐานข้อมูลจริง (ต้องรัน npm start ก่อน)
```

ทดสอบด้วยมือผ่าน [`requests.http`](requests.http): ติดตั้งส่วนเสริม REST Client ใน VS Code เปิดไฟล์ แล้วกด "Send Request" ไล่จากบนลงล่าง (สร้างสินค้า → ปรับสต็อก → ดูประวัติ) ทุกคำขอมีบรรทัด `Expect` บอกผลที่ควรได้ เช่น ลดสต็อกเกินคงเหลือต้องได้ `409 INSUFFICIENT_STOCK`

`npm test` มี 66 เคส ครอบคลุม validation ทุกฟิลด์, logic ปรับสต็อก (เพิ่ม/ลด/ลดจนเหลือ 0 พอดี/ลดเกิน/เกินขีดจำกัด), การ ROLLBACK เมื่อขั้นใดขั้นหนึ่งล้มเหลว, ลำดับคำสั่ง `FOR UPDATE` → `UPDATE` → `INSERT`, status code และรูปแบบ error ของทุก endpoint

ข้อควรทราบ: test ใน `npm test` จำลองฐานข้อมูลด้วย mock จึงไม่ได้พิสูจน์พฤติกรรมของ lock จริง ส่วนนั้นพิสูจน์ด้วย `npm run race-test`

## ข้อจำกัดและสิ่งที่ทำต่อได้

- ยังไม่มีระบบล็อกอิน/สิทธิ์การใช้งาน (อยู่นอกขอบเขตโจทย์)
- ยังไม่มีแก้ไขหรือลบสินค้า ถ้าต้องทำควรใช้ soft delete เพราะประวัติอ้างอิงสินค้าอยู่ (ตอนนี้ FK เป็น `ON DELETE RESTRICT`)
- เกณฑ์ใกล้หมดเป็นค่ากลางค่าเดียว ถ้าแต่ละสินค้าต้องการเกณฑ์ต่างกัน ให้เพิ่มคอลัมน์ `low_stock_threshold` ใน `products`
- หน้าเว็บยังไม่มี automated test (ตรวจด้วยการใช้งานจริงบนเบราว์เซอร์)
- ควรเพิ่ม integration test ที่รันกับ PostgreSQL จริงใน CI
